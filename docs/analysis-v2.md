## 2. 무엇이 바뀌었나

가장 큰 변화는 성공률보다 "확인된 성공"이다. v1에서는 성공한 28건 중 12건에서 에이전트가 결과를 확인하지 못했거나 실패했다고 보고했다. v2에서는 30건 모두 에이전트가 화면에서 결과를 확인하고 보고했다. 사람이 에이전트의 보고를 믿고 다음 일을 할 수 있다는 뜻이다.

| v1 실패·미확인 원인 | v2에서 막은 원칙 | 관찰 |
| --- | --- | --- |
| 작업 뒤 목록이 그대로라 "됐는지 모르겠다" | P3 자동 갱신 | v2의 미확인 성공 0건 |
| 실행 중 서버 삭제가 거부되자 "다른 방법이 없다"며 포기 (`delete-running-server` v1 2회차) | P8 비활성 이유 표시 | v2는 메뉴에서 "먼저 정지해야 삭제할 수 있습니다"를 읽고 정지부터 수행 |
| 반납 후 목록이 안 바뀌어 같은 서버를 다시 반납 → 404 → 혼란 (`cleanup-stopped-dev` v1 1회차) | P3, P4 | v2는 3/3 성공 |
| 2페이지에 숨은 서버를 찾느라 페이지를 오감 | P5 검색·필터·최근순 | snapshot 7.4 → 3.3회 |

## 3. v2에서도 남은 문제 (데이터가 찾아낸 것)

- 메뉴 버튼 이름의 "▾" 기호. 버튼의 접근성 이름이 "api-server-dev 작업 ▾"가 되어, 에이전트가 이름으로 찾으려다 7번 실패했다(`does not match any elements`). 장식 기호는 `aria-hidden`으로 뺐다(a275d5c, 재측정 전).
- 일부 시나리오는 v2가 더 오래 걸렸다. `count-prod`(6 → 8턴)는 에이전트가 새로 생긴 환경 필터를 쓰다가 도구 호출 형식을 틀렸고(`select_option` 6회 오류), `add-firewall-rule`(12 → 15턴)은 감독 패널이 "규칙 추가" 버튼을 가려 클릭이 실패했다(3/3). 에이전트는 Enter 키나 창 크기 변경으로 우회했다. 처음에는 "라벨이 늘어서"라고 잘못 분석했고, 이후 레이아웃을 고치고 폭별 E2E(`e2e/layout-v2.spec.ts`)를 추가했다. 필터를 쓰는 쪽이 정확하지만, 단계 수만 보면 손해였다.
- MCP와의 격차는 여전하다. v2도 MCP보다 약 3배 많은 턴과 5배 많은 토큰을 쓴다. 에이전트에게는 MCP 같은 구조화된 경로를 제공하고, 웹 화면은 사람이 에이전트를 감독하고 함께 쓰는 자리로 설계하는 것이 맞다는 근거다.
- MCP의 비동기 미확인 8건. 삭제·시작·정지 요청 직후 전이 상태에서 보고를 끝냈다. 도구 설명에 "완료까지 확인하라"는 안내나 완료 대기 도구가 필요하다 (원칙 P8의 API 버전).

## 4. 한계

- v1은 일부러 만든 기준선이다. NCP 공식 가이드와 대조한 결과([README 패턴 표](../README.md#콘솔-v1의-사용성-패턴)), 서비스 용어·다단계 생성·이름 입력 확인·비동기 반납은 NCP에도 있었다. 반면 이름 없는 새로고침 버튼과 검색 없는 목록은 NCP에는 없는 문제였다. 이 두 패턴이 원인이 된 실패(F1 일부, 페이지 탐색)만큼 v1 → v2 개선 폭이 과대평가되었을 수 있다.
- 확인 여부는 AI 한 명이 검수했다. 자동 분류 정규식도 같은 답변을 보고 보강했으므로 새 실행에서의 정확도는 검증되지 않았다.
- 모델 1종(Haiku), 시나리오당 3회. 성공률 차이(93% vs 100%)는 통계적으로 강하지 않다. 턴·토큰·확인된 성공률 차이는 일관되게 크다.
- 시나리오와 채점기를 같은 사람이 만들었다. 추가 시나리오 2개도 같은 사람이 미리 만들었으므로, 다른 사람이 만든 시나리오로도 검증해야 한다.
- IntentGuard 승인 흐름은 벤치마크에 포함하지 않았다. 측정 당시 10개 시나리오는 모두 낮은 위험이라 승인이 발생하지 않았다. 이후 운영 서버 정지를 위험 작업으로 바꿨으므로 재측정 때는 승인 정책을 끄거나 승인 과제로 따로 잰다. 승인 흐름은 스크립트 E2E로만 검증했다. 다음 단계로 위험한 요청이 섞인 시나리오에서 사람 개입 비율과 잘못된 실행 차단율을 측정한다.
