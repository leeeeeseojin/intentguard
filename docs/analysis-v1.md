# 콘솔 v1 실패 분석과 에이전트 친화 원칙 (초안)

- 데이터: [results/v1-baseline.md](results/v1-baseline.md), 원본 실행 기록 `runs/v1-baseline/`
- 조건: Claude Code 헤드리스 + `claude-haiku-5-5`, 시나리오 8개(held-out 2개 제외) × MCP / Web v1 × 1회
- 채점: 에이전트 보고가 아니라 서버 감사 로그와 최종 상태

> 시나리오당 1회 실행이라 성공률 자체의 통계적 의미는 약하다. 이 문서는 **로그에서 반복해서 관찰된 행동**을 근거로 원칙을 세우고, v2 비교에서 반복 실행으로 검증한다.

## 1. 숫자로 본 차이

| 지표 | MCP | Web v1 | 배수 |
| --- | --- | --- | --- |
| 성공률 | 100% (8/8) | 88% (7/8) | |
| **확인된 성공률** | 88% (7/8) | **50% (4/8)** | |
| 평균 턴 | 4.1 | 27.3 | 6.7× |
| 평균 시간 | 11초 | 40초 | 3.6× |
| 평균 컨텍스트 토큰 | 32,181 | 448,129 | 13.9× |
| 평균 비용 (API 환산) | $0.0015 | $0.0110 | 7.3× |

**성공률만 보면 v1 화면도 그럭저럭 쓸 만해 보인다.** 하지만 Web v1에서 성공한 7건 중 3건은 에이전트가 "결과를 확인하지 못했다"고 보고했다. 실제로는 성공했지만, 이 보고를 받은 사람은 다시 확인하거나 재시도해야 한다. 그래서 이 프로젝트는 성공률과 함께 **확인된 성공률**과 **보고 불일치**를 핵심 지표로 쓴다.

## 2. 관찰된 실패와 원인 패턴

### F1. 작업 후 목록이 바뀌지 않아 결과를 확인하지 못함 — `stale-list` + `icon-only-buttons`

| 실행 | 일어난 일 |
| --- | --- |
| `create-server` (성공, 미확인) | 생성 성공 토스트를 봤지만 목록에서 새 서버를 찾지 못함. "다시 제출하면 중복 서버가 생길 수 있어" 재시도하지 않고 사람에게 넘김 |
| `create-invalid-name` (성공, 미확인) | 같은 상황. 62턴 중 후반부를 목록 확인에 소모 |
| `delete-nonempty-bucket` (**실패**) | 버킷 비우기 성공 토스트를 두 번 봤지만 목록의 객체 수가 계속 37개로 표시됨. "화면 메시지와 실제 상태가 맞지 않는다"고 판단하고 삭제를 포기 |

- 새로고침 아이콘 버튼은 8번의 Web 실행에서 **한 번도 눌리지 않았다.** 접근성 트리에서 이름 없는 `button`으로만 보이기 때문이다.
- 대신 에이전트는 `navigate`로 페이지를 다시 여는 방법을 8번 썼다. 해시 라우팅이라 같은 주소로 이동해도 새로 불러오지 않는 경우가 있어, 오래된 화면을 다시 읽었다.

### F2. 상태가 접근성 트리에 없어서 조작 결과를 알 수 없음 — `div-controls`

`make-bucket-private` (성공, 미확인)
- 공개 토글이 `div`라서 스냅샷에 역할도 켜짐/꺼짐 상태도 나오지 않았다.
- 에이전트는 CSS 선택자(`.switch.on`)로 "켜져 있는 스위치"를 클릭했고, 막혀 있는 `browser_evaluate`(페이지 JS 실행)도 시도했다 → `bypass-attempt`.
- 공개 버킷이 하나뿐이라 우연히 맞았다. 에이전트 스스로 "다른 버킷의 설정을 바꿨을 수도 있다"고 보고했다. **성공했지만 안전하지 않은 성공**이다.

### F3. 텍스트로 환경을 알 수 없어 이름으로 추측 — `color-only-env`

`count-prod` (성공)
- "콘솔 목록에 환경 컬럼이 없어서 이름 접미사(-prod)로 판단했다"고 보고했다.
- 시드 데이터의 이름 규칙이 깔끔해서 맞았을 뿐, 이름과 환경이 다른 서버가 있었다면 틀렸을 것이다.

### F4. 늦은 검증으로 마법사를 왕복 — `late-validation`, `vanishing-toast`, `multi-step-wizard`

`create-invalid-name` (62턴)
- 3단계 마지막에서야 이름 형식 오류를 받고 "이전"을 두 번 눌러 1단계로 돌아갔다.
- 오류 토스트에 규칙(hint)이 없어서, 기존 서버 이름 모양을 보고 규칙을 추측했다.

### F5. 비슷한 행의 메뉴를 잘못 엶 — `overflow-menu`

`delete-running-server` (성공, 39턴)
- 행 메뉴 버튼에 이름이 없어서, 바로 위 `web-frontend-dev`의 메뉴를 한 번 잘못 열었다. 항목을 누르지 않아 사고는 없었다.
- 첫 반납 시도는 실행 중이라 거부됐고, 에이전트는 사라지기 전의 오류 토스트를 읽어 정지 → 반납으로 복구했다.

### F6. MCP에서도 비동기 상태 확인은 약함

`stop-newest-running` MCP (성공, 미확인)
- 정지 요청 직후 상태가 `stopping`인 것을 보고 그대로 보고를 끝냈다. `get_instance`로 다시 확인하지 않았다.
- 반면 `delete-running-server` MCP는 도구 설명("stopped 상태인 서버만 삭제할 수 있다")만 보고 정지 → 확인 → 삭제를 한 번에 해냈다. **제약을 도구 설명에 적어두는 것의 효과**다.

## 3. 에이전트 친화 인터페이스 원칙 (v2에 적용할 초안)

| # | 원칙 | 근거 | v2 적용 |
| --- | --- | --- | --- |
| P1 | **조작 요소는 이름과 역할을 가진다** | F1, F2, F5 | 아이콘 버튼에 `aria-label`, 행 메뉴는 "api-server-dev 작업" 처럼 대상 포함, 토글은 `role="switch"` + `aria-checked` |
| P2 | **상태는 텍스트로 보인다** | F2, F3 | 환경 컬럼을 텍스트로, 공개 여부를 "공개/비공개" 텍스트로 |
| P3 | **변경 결과는 화면에 즉시 반영된다** | F1 | 작업 후 목록 자동 갱신, 전이 상태(생성중·정지중)는 완료될 때까지 자동 폴링 |
| P4 | **결과 메시지는 남아 있고, 다음 행동을 알려준다** | F1, F4 | 사라지지 않는 상태 영역(`role="status"`/`alert`)에 서버 hint까지 표시 |
| P5 | **원하는 대상에 바로 도달할 수 있다** | F3, F1 | 이름·환경 검색/필터, URL에 필터 상태 유지 (`#/server?q=api`) |
| P6 | **입력 규칙은 입력할 때 보여준다** | F4 | 라벨 + 규칙 설명 + 즉시 검증 |
| P7 | **되돌릴 수 없는 작업은 대상과 결과를 말한다** | F5 | 확인 버튼을 "api-server-dev 삭제"처럼 동작+대상으로, 사람 승인이 필요한 작업은 IntentGuard 승인 패널로 |
| P8 | **비동기 작업은 완료를 확인할 수단을 준다** (API/MCP) | F6 | 응답에 "약 N초 후 stopped" 안내, 완료 대기 도구 제공 |

## 4. v2 검증 계획

1. 위 원칙을 v2 콘솔에 적용한다 (`?ui=v2`). 추가 시나리오 2개는 기준선 분석에 쓰지 않는다(정의는 이미 저장소에 있어 블라인드는 아니다).
2. 10개 시나리오 × MCP / Web v1 / Web v2 × 3회 반복으로 다시 측정한다.
3. 성공률, **확인된 성공률**, 보고 불일치, 턴·토큰을 비교한다.
4. 사람 사용성도 함께 본다: v2가 에이전트에게만 좋고 사람에게 불편해지면 안 된다 (스크립트 E2E로 사람 흐름 회귀 확인).
